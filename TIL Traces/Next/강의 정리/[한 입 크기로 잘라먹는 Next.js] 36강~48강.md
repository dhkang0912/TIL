## 36강 앱 라우터의 데이터 페칭
- 페이지 라우팅에서는 모든 컴포넌트가 클라이언트 컴포넌트이기 때문에 서버에서만 실행되는 함수를 통해서 서버 렌더링을 진행함
- 모든 컴포넌트가 서버에서 한번, 클라이언트에서 한번 렌더링됨
  1. SSR(서버 사이드 렌더링) : getServerSideProps
  2. SSG(정적 사이트 생성) : getStaticProps
  3. Dynamic SSG(동적 경로에 대한 정적 사이트 생성) : getStaticPaths, fallback
  - 최상단의 컴포넌트에서 하단의 모든 페이지들 다 렌더링되어야 함 (최상단의 컴포넌트에서 데이터를 다 하위로 보내줘야 함)

### 앱 라우터에서 데이터 페칭
- 서버 컴포넌트를 비동기 함수로 작성하여 데이터 페칭
- 클라이언트 컴포넌트에는 브라우저 동작 시 문제를 일으킬 수 있기 때문에 Async 키워드를 사용할 수 없었음
- 데이터가 필요한 경우 ***해당 컴포넌트에서 직접 데이터를 불러올 수 있음***

### env 파일 설정
- NEXT_PUBLIC 이라는 말을 키 앞에 불려주지 않으면 자동으로 서버 측에서만 불러올 수 있게 됨
- 붙인 경우 클라이언트에서 설정할 수 있게 됨


### ***하면서 들었던 의문 - useSearchParams와 searchParams를 왜 다르게 사용할까?***
- 클라이언트 컴포넌트인 경우에는 ```useSearchParams``` 만 사용가능
- 서버 컴포넌트는 ```searchParams```만 사용 가능

## 37강 데이터 캐시
- fetch 메서드를 활용해 불러온 데이터를 Next 서버에서 보관하는 기능 (axios에서는 사용 불가능)
- 영구적으로 데이터를 보관하거나, 특정 시간을 주기로 갱신 시키는 것도 가능
- 불필요한 데이터 요청의 수를 줄여서 웹 서비스의 성능을 크게 개선할 수 있음

- fetch 요청에서 두번째 인자로 캐시되는 조건을 넣어줌
- 두번째 인자에 캐시 조건을 넣지 않는다면 기본이 캐싱을 하지 않는 것
```js const response = await fetch(`~/api`, {cache:"force-cache"})```
### cache:"force-cache"
- 요청의 결과를 무조건 캐싱함
- 한번 호출된 이후에는 다시는 호출되지 않음
- 캐싱이 안 되어있는 경우 (첫 요청 시) `miss`라고 판정됨
  - 이후 백엔드 서버에서 데이트를 가져온 경우 `set` 판정되어 저장하게 됨
  - 이후 접속 요청 시 이미 데이터를 캐싱해놓았기 때문에 `HIT` 판정으로 이미 캐싱된 데이터를 가져옴

### cache:"no-store"
- 데이터 페칭의 결과를 저장하지 않는 옵션
- 캐싱을 아예 하지 않도록 설정하는 옵션
- 데이터 캐시를 캐싱하지 않고 백엔드 서버에 항상 요청하고 응답을 받음

### next:{revalidate:10}
- 특정 시간을 주기로 캐시를 업데이트 함
- 마치 Page Router의 ISR 방식과 유사함
- 첫 요청 시 `miss` => 백엔드 서버에서 가져와서 저장하고 `set` => 기간 내라면 `hit` 판정이 나고 캐시된 데이터를 찾아서 사용함
  - 유효기간이 지나면 `stale(상함)` 상태로 변경되고 우선 캐시된 데이터를 보여줌
  - 이후 revalidate하여 다시 백엔드 서버에서 `set` 상태로 저장하게 되고 다시 `hit` 판정으로 최신 데이터를 가져옴


### next:{tags:['a']}
- 요청이 들어왔을 때만 데이터를 최신화함
- On-Demand ISR 같은 방식

## 38강 리퀘스트 메모이제이션
- request memoization : 요청을 기억함
- 서버 측에서 렌더링하는 과정에서 중복적으로 발생하는 데이터 요청을 중복을 제거하여 한번만 요청하게 자동으로 data-fetching을 최적화함
- ***하나의 페이지를 렌더링하는 동안에 중복된 API 요청을 캐싱하기 위해 존재하여 렌더링이 종료되면 모든 캐시가 소멸됨***
  => 서버 컴포넌트의 도입으로 데이터의 페칭 패턴이 달라졌기 때문에 이뤄짐 (각 컴포넌트가 필요한 데이터를 요청하게 됨)
  => 서로 다른 컴포넌트에서 동일한 데이터를 필요로 하는 경우가 발생

- 데이터 캐시는 백엔드 서버에서 불러온 데이터를 서버가 가동 중이면 거의 영구적으로 저장하게 됨 => 차이가 있음

## 39강 풀 라우트 캐시1
- Next 서버 측에서 빌드 타임에 특정 페이지의 렌더링 결과를 캐싱하는 기능
- 빌드 타임에 특정 주소를 가진  페이지를 렌더링할 때 리퀘스트 메모이제이션과 데이터 캐시를 통해 `풀라우트 캐시`라는 이름으로 생성을 해놓음
  - 이미 풀라우트 캐시가 된 페이지는 `hit` 되어있으므로 아주 빠르게 접속 요청이 됨
- 정적 사이트 생성 (SSG)와 유사함
- 모든 페이지들은 기능에 따라 `정적 페이지`와 `동적 페이지`로 나눠짐

### Dynamic Page
- 특정 페이지가 접속 요청을 받을 때마다 매번 변화가 생기거나, 데이터가 달라질 경우

1. 서버 컴포넌트에서 캐시되지 않는 Data Fetching을 사용할 경우
  - 기본 설정이거나 {cache:"no-store"}라고 설정되어있는 경우

2. 동적 함수(쿠키, 헤더, 쿼리스트링)을 사용하는 컴포넌트가 있을 때
  - 내용이 달라질 수 있는 정보를 받아오는 서버 컴포넌트일 때

### Static Page
- Dynamic Page가 아니면 모두 Static Page가 됨

### 풀 라우트 캐시 분류 이미지
![!\[alt text\](image.png)](<풀 라우트 캐시.png>)
- 동적 함수가 없고 데이터 캐시가 되는 경우에만 Static Page로 분류되어 풀 라우트 캐시가 됨
- 풀 라우트 캐시도 revalidate가 가능 (ISR처럼)
- 만약 해당 페이지의 컴포넌트 중 하나의 데이터 페칭이라도 revalidate가 붙어있다면 데이터 캐시가 `stale`인 경우 해당 페이지의 풀 라우트 캐시도 `stale`로 변경되고 다시 데이터를 받아와서 페이지를 최신화함 


## 40강 풀 라우트 캐시2
- 클라이언트에서 값을 넘겨줘야만 동작하는 경우(searchParams)의 경우 빌드 타임에는 알 수 없어서 에러가 뜸
- 클라이언트 컴포넌트로만 동작하도록 아래와 같이 Suspense로 묶어줘야 함
```js
<Suspense fallback={<div>Loading...</div>}>
  <Searchbar />
</Suspense>
```

- Suspense의 기능 : 묶어있는 컴포넌트의 비동기 작업이 완료될 때까지 미완성 상태로 남겨놓음
  - useSearchParams와 같이 클라이언트 작업은 비동기로 되고 해당 내용이 불러와져야 종료됨

## 41강 풀 라우트 캐시 3. 동적 경로에 적용하기
- query string과 같은 동적 함수를 사용하는 페이지에는 static으로 할 수 없어서 풀 라우트 캐시는 포기해야 함
- 대신 데이터 캐싱은 가능함
- book-item을 검색한 결과에 대하여 데이터 캐싱으로 가지고 있으면 이미 캐싱된 경우에는 더 빠르게 보여줄 수 있음

- generateStaticParams 함수를 통해서 dynamic routing을 쓰더라도 특정 페이지가 빌드 타임에 만들어져야 하는지를 지정하여 빌드 타임에서 생성해놓을 수 있음 
  - url parameter를 명시할 때는 문자열로만 가능
  ```js
  export function generateStaticParams() {
  return [{ id: "1" }, { id: "2" }, { id: "3" }];
  }
  ```
  - 이렇게 지정하여 작성하면 존재하지 않아도 무조건 정적 페이지로 생성하게 됨
  - `getStaticPaths`의 기능과 동일
  - 만약 이미 지정하지 않은 경로라도 풀 라우트 캐시로서 생성하여 저장됨
  - 없는 페이지의 경우 아래와 같이 설정하면 404 페이지로 넘어감
  ```js
    if (response.status === 404) {
      notFound();
    }
    ```
  - 만약 dynamic routing이더라도 지정한 페이지가 아니면 모두 404로 지정하고 싶은 경우 아래와 같이 상단에 작성해줌
  ```js
  export const dynamicParams = false;
  ```

  ## 42강 라우트 세그먼트 옵션
  - 페이지의 동작을 강제로 세팅할 수 있음
  - `export const dynamic = ''`
  1. auto : 기본값, 아무것도 강제하지 않음
  2. force-dynamic : 페이지를 강제로 dynamic 페이지로 설정 (권장 X)
  3. force-static : 페이지를 강제로 static 페이지로 설정 (권장 X)
  4. error : 페이지를 강제로 static 페이지 설정 (설정하면 안되는 이유가 있는 경우 -> 빌드 오류)

## 43강 클라이언트 라우터 캐시
- 브라우저에 저장되는 캐시로 자동으로 동작됨
- 페이지 이동을 효율적으로 진행하기 위해 페이지의 일부 데이터를 보관함
- 페이지의 레이아웃에 해당되는 RSC는 클라이언트 라우터 캐시에 저장하게 됨
- 서버로부터 중복되게 불러오지 않기 위해 사용
- 클라이언트 라우터 캐시를 사용한 경우 새로고침을 하거나 다시 페이지에 접속하면 캐시가 삭제됨

## 44강 스트리밍이란?
- 스트리밍 : 데이터가 크거나 서버 측에서 데이터를 준비해야하는 시간이 오래 걸려서 데이터를 빠르게 보내기 어려울 때 데이터를 잘게 쪼개서 물가에 흘려보내듯 보내는 것
- 사용자에게 긴 로딩 없이 볼 수 있음
- HTML 파일을 스트리밍하는 기능 제공
- 느리게 렌더링 되는 부분은 로딩바 같은 걸 보여주고 빨리 렌더링되는 부분만 먼저 보여줌
- 비동기로 데이터를 불러오는 컴포넌트는 로딩바를 보여주고 즉시 보여줄 수 있는 컴포넌트를 먼저 보여주고 데이터가 불러와지면 데이터를 보여줌
- Dynamic Page에 자주 사용됨
- 오래 걸리는 컴포넌트의 렌더링을 사용자가 좀 더 좋은 환경에서 기다릴 수 있도록

## 45강 스트리밍 1. 페이지 스트리밍
- 스트리밍하고자 하는 페이지와 동일한 위치에 `loading.tsx`로 페이지를 만들면 자동으로 스트리밍하게 됨
- 해당 경로 아래 모든 컴포넌트가 스트리밍이 걸릴 수 있게 함 (마치 layout처럼)
- async가 붙어서 비동기로 되어있는 컴포넌트에만 스트리밍됨
- 페이지 컴포넌트에만 적용 가능
- url이 완전히 변경된 게 아니라 query string만 변경되는 경우 해당 되지 않음

## 46강 스트리밍 실습 2. 컴포넌트 스트리밍
- Suspense로 감싸진 경우 비동기로 데이터가 받아온 이후에 동작하게 되면서 스트리밍을 할 수 있음
- Suspense를 이용해도 기본적으로 한번 로딩이 맞춰지면 다시 로딩하지 않지만 key를 적어줘서 새로운 컴포넌트로 인식해서 화면에 다시 그리도록 함

```js
<Suspense fallback={<div>Loading...</div>} key={q}>
  <SearchResult q={q || ""} />;
</Suspense>
```
- 다양한 컴포넌트가 있을 때 각각 로딩 화면을 설정하여 보여줄 수 있음

## 47강 스켈레톤 UI 적용하기
- 페이지가 로딩되는 중에 대략적으로 비슷한 UI를 보여주기
- 스켈레톤 UI 만들어서 컴포넌트화해서 fallback에 넣기

```js
import BookItemSkeleton from "./book-item-skeleton";

export default function BookListSkeleton({ count }: { count: number }) {
  return new Array(count)
    .fill(0)
    .map((_, idx) => <BookItemSkeleton key={`book-item-skeleton=${idx}`} />);
}

```
- 개별 아이템을 이런 식으로 전체 스켈레톤으로 만들 수 있음
- React Loading Skeleton 이라는 라이브러리도 있음

## 48강 에러 핸들링
- 서버, 클라이언트 모두 에러를 핸들링 할 수 있게 클라이언트 컴포넌트로 만들어줄 것
- 같은 경로에 `error.tsx` 파일을 만들면 에러가 발생할 경우 해당 파일의 내용이 렌더링됨

```js
"use client";

import { useRouter } from "next/navigation";
import { startTransition, useEffect } from "react";

export default function Error({
  error,
  reset,
}: {
  error: Error;
  reset: () => void;
}) {
  const router = useRouter();

  useEffect(() => {
    console.error(error.message);
  }, [error]);

  return (
    <div>
      <h3>오류가 발생했습니다.</h3>
      {/* reset은 서버 컴포넌트를 다시 실행하지는 않음, 클라이언트 컴포넌트 내부 오류만 복구 가능 */}
      {/* <button onClick={() => reset()}>다시 시도</button> */}
      {/* <button onClick={() => window.location.reload()}>다시 시도</button> */}
      <button
        onClick={() => {
          // 현재 페이지에 필요한 서버 컴포넌트들을 다시 실행해주는 기능을 함
          // 서버 컴포넌트 재렌더링
          // startTransition는 안의 컴포넌트를 일괄적으로 수정해줌
          startTransition(() => {
            router.refresh;
            // 에러 상태를 초기화, 컴포넌트들을 다시 렌더링
            reset();
          });
        }}
      >
        다시 시도
      </button>
    </div>
  );
}
```
